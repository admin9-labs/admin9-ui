## 组件职责边界

### AFilePicker

- 核心职责仅为浏览已有文件、类型和分组筛选、搜索、分页、选择与确认。
- 保留“上传文件”入口；点击后组合调用独立 `AFileUploader`，不再自行实现上传队列和上传交互。
- 上传结束后返回文件库，刷新准确分页与统计。

### AFileUploader

- 新增为公开组件，可独立使用。
- 独立承担上传事务：选择来源、目标分组、批量队列、校验、进度、失败提示、重试或移除、完成回传。
- 默认支持本地多选上传。
- 本地、网络文件、扫码上传等来源采用 capability/adapter 驱动；宿主未提供能力时不显示对应方式。
- 组件库不得假设具体后端、URL、二维码服务或业务字段。
- 可被 `AFilePicker` 和消费应用单独复用。

## 关键交互语义

### 从 AFilePicker 发起上传

- 优先在同一弹层内切换到上传子视图或上传步骤，并提供“返回文件库”；默认避免 Modal 叠 Modal。
- 上传成功后刷新目标类型和分组对应的列表。
- 单选场景默认选中第一条成功记录。
- 多选场景在剩余选择额度内选中成功记录。
- 不自动提交父级选择；回到文件列表后仍由用户确认。
- 超出额度或部分失败时必须明确反馈，成功项不能因部分失败而丢失。

### 独立使用 AFileUploader

- 通过事件或返回值交付成功的 `FileItem[]`。
- 不绑定宿主表单。

### 文案

- 区分“选择文件/文件库”和“上传文件”。
- 在确定具体类型的上下文中，可以显示“选择图片/上传图片”等类型化文案。

## 文件类型与分组约束

- 现有文件模型以真实 `FileType` 为第一层级，分组从属于具体类型。
- 上传目标分组必须与文件的具体真实类型一致。
- 上传上下文只允许一种真实类型时，可以提供单一“上传至分组”选择。
- 允许混合类型批量上传时，不得把一个类型的 `groupId` 应用于全部文件。
- 混合类型场景需要按文件真实类型分配分组，或者只在单类型上下文显示目标分组。
- 实现前必须根据现有 adapter/API 契约确定最小可行方案，不预先虚构后端能力。

## 上传状态与契约要求

至少覆盖以下状态和行为：

- `pending`、`uploading`、`succeeded`、`failed`。
- 文件数量、文件类型、文件大小等由宿主配置的校验。
- adapter 能提供进度时展示确定进度；不能提供时展示不确定进度。
- 部分成功语义、失败原因、重试和取消。
- 完成结果只包含通过现有 `FileItem` 规则校验的成功项。
- 防重复提交。
- 关闭时仍有上传任务的处理。
- 组件卸载后的异步回调安全。

## 兼容与迁移要求

- 设计或实现前先检查现有 `FilePickerAdapter`、`FileUploadCapability` 和全部公开类型。
- 新增独立上传契约后，现有上传配置应能暂时映射到 `AFileUploader`。
- 通过文档和废弃标记提供渐进迁移路径。
- 本包继续保持 backend-agnostic，不引入具体 API、鉴权、store、route、权限或业务字段。

## 复核修订（2026-08-19）

本节基于当前源码、文档和测试复核形成，是后续详细设计与实现的有效输入。核心结论仍是抽出可复用的上传 UI 和上传事务流程，但以下内容修订并覆盖初版表述。

### 明确覆盖的初版表述

1. 初版将 `AFilePicker` 描述为核心职责仅浏览已有文件，容易被理解为“纯浏览组件”。修订后，`AFilePicker` 的公共职责是完整文件选择工作流。
2. 初版把网络文件和扫码上传与本地上传并列为首期 capability/adapter 方向。修订后，第一阶段只承诺现有真实契约能够支持的本地批量上传；网络文件和扫码上传仅保留为未来产品参考，不固化公开 API。
3. 初版优先指定同一 Modal 内上传子视图。修订后，需求阶段不锁定 UI 容器，只要求流程连续且不得同时激活两个焦点陷阱。

初版中“新增独立公开组件 `AFileUploader`”也调整为候选结论：是否公开须由详细设计证明其通用复用价值；否则先作为 internal 实现。

### AFilePicker 的有效职责

- `AFilePicker` 负责完整的文件选择工作流：打开文件库、浏览和筛选、维护草稿选择、确认写回。
- Picker 可以保留上传入口，并负责上传完成后的列表刷新以及成功项与选择草稿的协调。
- 上传队列、上传 UI 和上传异步生命周期交给候选 `AFileUploader`。
- 重构必须保留现有上传成功语义：校验 `FileItem`、拒绝重复 ID、错误类型、pending 状态和空 URL，并在 limit 允许范围内自动加入草稿。
- 最终仍由用户确认后写回 `v-model`，不得因拆分组件直接改变既有行为或兼容性。

### Picker 与应用文件管理页的边界

参考图 2 同时包含“使用选中图片”、搜索、分组、分页、删除和移动，是选择器与管理页面混合的产品界面。本包只借鉴上传流程独立，不照搬其混合边界。

- `AFilePicker` 继续不提供删除、移动或分组管理。
- 删除、移动和分组管理属于消费应用。
- `AFileUploader` 可由 Picker 和消费应用复用。

### 现有服务契约与优先目标

- 当前 `FileUploadCapability` 已是独立能力，`FilePickerAdapter` 按能力组合浏览与可选上传。
- 第一优先级是让 Picker 与消费应用复用上传 UI 和上传事务状态。
- 现有 `upload(options): Promise<FileItem>` 是单文件契约，足以由上传组件对多个 `File` 分项调用并组织批量队列。
- 除非真实后端合同证明需要，不新增臆造的 batch API。

### 第一阶段能力范围

第一版候选 `AFileUploader` 只承诺：

- 本地文件批量选择。
- 对每个文件分项调用现有上传能力并维护队列。
- 绑定具体文件类型和该类型下的目标分组。
- 进度、不确定进度、取消、失败重试和完成结果。
- 部分成功时保留成功项，不因其他项失败而回滚。

网络文件和扫码上传只作为未来扩展参考：

- 扫码上传依赖会话、二维码生成、轮询或推送、过期和鉴权，超出现有通用 `upload(File)` 契约。
- 网络文件涉及 SSRF、下载校验和文件归属，也超出现有契约与安全边界。
- 只有取得真实消费方和 API 合同，并证明能力可跨项目复用后，才考虑新增相应 capability；否则由消费应用自行实现。

### 上传与业务选择分离

- `AFileUploader` 独立使用时只返回通过校验的成功 `FileItem[]`，不负责业务选择或表单写回。
- 被 `AFilePicker` 组合时，Picker 对成功项逐项执行资格、重复 ID、类型和 limit 校验，再加入草稿。
- Picker 不自动确认，最终仍由用户点击确认写回 `v-model`。
- 部分失败不得回滚或丢失已成功的项目。

### 具体类型与分组规则

- `FileGroup` 隶属于具体 `FileType`，每次上传必须处于一个具体类型上下文。
- 第一版不提供混合真实类型文件的一键批量上传。
- 每个上传队列绑定一个 concrete `FileType` 以及该类型下的 `groupId` 或 `null`，与现有 `FileUploadOptions` 保持一致。
- “默认支持多选上传”仅表示同一上传上下文中可选择多个文件，不表示允许混合真实类型，也不绕过 `accept` 或后端校验。
- 组件不依据 MIME 或扩展名擅自把文件分类为不同真实 `FileType`。

### UI 容器的设计约束

需求阶段不预先锁定上传容器。详细设计可以比较：

- 同一 Modal 内的上传子视图。
- 文件库 Modal 与上传 Modal 串行切换。
- 可嵌入的上传面板。

无论采用哪种方案，都必须满足：

- 上传流程与文件库流程连续。
- 不同时激活两个焦点陷阱。
- 保留 Picker 草稿、当前类型和分组。
- 返回文件库后正确刷新，并恢复到合理焦点位置。

### 是否作为公开组件

根据仓库 `AGENTS.md`，公开组件必须填补 Arco Design Vue 的广泛通用缺口。`AFileUploader` 不能只是对 `a-upload` 的薄包装。

只有详细设计能够证明它统一承担以下能力，并能被 Picker 和消费应用复用时，才作为公开组件：

- 批量上传队列。
- `FileUploadCapability` 适配。
- 具体类型与分组上下文。
- 部分成功语义。
- 取消和失败重试。
- 完成结果校验。

若详细设计后通用复用价值不足，应先作为 internal 实现，不为了增加组件数量而强行公开。

### 后续阶段入口

下一阶段仍需收到明确指令后才能开始。详细设计必须先基于现有契约提出最小方案，并说明：

- 复用上传事务状态的内部边界。
- Picker 如何组合且保持现有语义。
- 是否满足公开组件标准。
- 兼容性、测试、locale、文档、验收宿主、焦点和无障碍方案。

本次复核仍只记录需求，不开始实现，不修改公开 API、版本或变更日志，不提交、不发版。

## 2026-08-20 浏览器复核反馈

本节来自验收宿主的实际交互复核，覆盖此前“上传成功项自动加入 Picker 草稿”和默认格式提示相关表述：

- 上传队列只在上传进行中或需要处理失败、取消任务时显示。全部成功后自动关闭并清空；存在失败或取消时保留，以便重试、移除或手动关闭。
- `AFilePicker` 上传完成后刷新当前具体类型和分组的列表，但不自动选择成功项，不改变选择草稿，也不写回 `v-model`。用户必须在列表中显式选择并确认。
- `accept` 改为完全可选的原生文件选择提示。Picker 和独立 Uploader 默认都不按当前 `FileType` 推导 MIME 或扩展名限制；只有宿主显式传入时才限制原生选择器。
- 现有 `FileUploadCapability` 仍要求每个上传队列绑定具体 `FileType` 和该类型下的 `groupId/null`。这里的 `FileType` 是 adapter 接收的业务目标分类，不等于浏览器文件格式过滤，也不授权组件依据 MIME 或扩展名自行分类。
- adapter 和后端仍负责真实文件内容、MIME、扩展名、大小、安全、归属以及目标类型和分组权限校验。

本节正式进入实现与验收，覆盖文档中此前“仅记录、不修改代码”的阶段状态；仍不授权提交或发布。

## 2026-08-20 聚合视图与并发追加复核

- Picker 的上传入口在聚合“全部”视图中也必须可选择文件，不再要求用户先切换到具体类型。
- 底层 adapter 契约不变，仍不传 `all` 或 `undefined`。实际目标类型按“当前具体类型、最近使用的具体类型、第一允许类型”解析；聚合视图下目标分组固定为 `null`，界面提示实际目标类型。
- 上传进行中不得禁用文件选择入口。后续选择的文件追加到当前 concrete `FileType` 和 `groupId/null` 队列，并与已有活动任务一起结算。
- 显式 `disabled`、Picker 无允许类型或缺少上传 capability 仍按原有约束阻止上传；“任何时间可选择”不绕过这些宿主和契约级禁用条件。
